# Datos para recibos y revisión de transferencias

- `/dashboard/wallet` guarda datos declarados por el profesional autenticado mediante `GET/PUT /api/billing/profile`. El servidor valida formato y límites; **no verifica la validez tributaria ante el SRI**. No se emiten facturas electrónicas.
- Al asignar un pago a un contacto, `PaymentAllocation.billingSnapshot` conserva los datos para ese recibo. Editar el perfil no reescribe recibos anteriores. Los pagos históricos sin snapshot usan únicamente nombre y correo de cuenta, sin inventar datos fiscales antiguos. El cierre de cuenta elimina el perfil fiscal y anonimiza sus snapshots.
- Los pagos asignados permiten descargar un PDF privado mediante `GET /api/payments/:id/receipt`, solo para el titular activo del mismo tenant. Los pagos pendientes o de otras cuentas no tienen descarga. El recibo no incluye datos de contacto ni direcciones del cliente.
- Los **recibos de transferencias** siguen el outbox existente: llegan al correo de la cuenta profesional, con copia al correo de facturación declarado al asignar el pago si difiere. El PDF va adjunto; el enlace al historial requiere autenticación. No se añaden avisos automáticos de recibo a tarjeta ni PayPhone en este cambio. La entrega SMTP puede reintentarse y duplicarse; aceptación SMTP no demuestra lectura del mensaje.
- Al presentar un comprobante de transferencia, se encola un aviso individual para cada miembro activo, con correo verificado y permiso `payments.review` en el tenant. El permiso se vuelve a comprobar al entregar. El correo no incluye el comprobante. En **Administración → Transferencias**, un revisor autorizado puede ver los correos que recibirían avisos. Para confirmar que una dirección particular está cubierta, verifica allí su presencia; si no figura, configura una membresía y rol adecuados mediante el flujo administrativo. No se codifican destinatarios fijos ni se consulta producción desde el repositorio local. También hay que revisar «Correos fallidos» y comprobar SMTP en un entorno autorizado.
- Para publicar estos cambios se necesita aplicar `20261129000000_billing_receipts` antes de arrancar el backend nuevo, y compilar API y frontend. Esto **no** ha sido desplegado. Las pruebas automatizadas se ejecutan contra PostgreSQL aislado; no prueban entrega real ni emisión SRI.
